# Android app: architecture, setup and limits

> Written 25 Nov 2026 with the first version of `android-app/`. **Read §0 before trusting anything here:** the native code has been written and syntax-checked but **not yet compiled or run on a phone**. The first GitHub Actions build is the first real compile.

## 0. What is proven and what is not

| Part | Status |
|---|---|
| Database: attendance (`0110`) and Android/push/widget (`1401`) | Applied to an empty Postgres and tested (full suite passes: 41 assertions for `1401`, the attendance suite for `0110`, plus a mutation check that the widget permission test really fails when the rule is removed). **Not yet applied to the live project.** |
| Edge Functions `notify-push`, `widget-today` | Type-checked with Deno; the pure helpers (RS256 sign-in, message building, Firebase answer reading, widget request) are unit tested. **Never run against real Firebase or a live project.** |

| Android project (`android-app/`) | Generated by Capacitor 8.6.2; Java written by hand; `scripts/check-shell.mjs` and a Java syntax pass are clean. **Never compiled** (the authoring environment cannot reach Google's Android build servers). Expect a first-build error or two to fix. |

## 1. The idea

**Do not build an Android copy of Dua. Build an Android extension of Dua.**

```
dua.duapharma.com (the web app, deployed from main by GitHub Pages)   ← all modules, all screens, all business rules
        ▲  the APK just opens this address (capacitor.config.json: server.url)
Dua APK (Capacitor)  ─ push (Firebase) ─ location + mock flag ─ Today's Sale widget
        ▼
Supabase: Auth · RLS · database functions · Edge Functions notify-push, widget-today
```

The APK contains no Dua screens. A web change reaches every phone the moment it is deployed. The APK changes only when the **native** part changes.

## 2. What needs a new APK, and what does not

| Change | New APK? |
|---|---|
| Any web screen, module, report, rule | No |
| Attendance places, distance, GPS accuracy limit, "app required" | No (owner screen, `attendance.manage`) |
| Who receives which alert (`app_push_rules`) and the alert wording | No |
| Widget figures, who may see them, the owner's cash/card/credit split | No (server decides on every refresh) |
| New widget on the same data | Probably no (the engine is the Edge Function; a new *layout* is native) |
| New native permission, new widget layout, new plugin, Capacitor or Firebase upgrade, new icon | **Yes** |

Android never installs an update silently from a downloaded APK: the person taps Install and confirms. Keep the version number rising (the workflow uses the run number as `versionCode`).

## 4. Attendance

**Rule: the phone reports, the server decides.** The app sends latitude, longitude, accuracy and Android's "mock location" flag. `mgmt_attendance_check_in` measures the distance to the nearest active place and refuses, in this order: not from the app (when required), mock location, GPS accuracy worse than the limit, no place set, outside the place, "already in" / "not in". Check-in and check-out must alternate (a forgotten check-out stops blocking after 24 hours, so night shifts work).

- Every attempt is kept (`mgmt_attendance`, append-only), including refused ones, with the reason and the distance.
- The owner gets a push for **mock location** and **outside** attempts (once per person per day per reason; the alert carries no name or place).
- Staff see only their own last 24 hours. Only `attendance.view_all` sees everyone.
- Permissions: `attendance.check_in` (staff), `attendance.view_all`, `attendance.manage` (owner). **No role preset carries any of them** (the contract and the core tests require the owner to approve presets). Give `attendance.check_in` to each person in Users & Access, or add a `role_permissions` row in a new migration to make it a role default.
- **Honest limit:** this stops standing outside the shop and casual fake-GPS apps that Android flags. A rooted phone that hides the flag, or someone with a friend holding their phone at the shop, is not stopped. Stronger proof would need Play Integrity, which is a later project.
- Setting the place: open Manager → Attendance on the phone while standing in the pharmacy → Add a place → "Use my location now" → set the distance (100 m is a sensible start; indoor GPS can be off by 30–60 m).

## 4b. Automatic attendance (Phase 4 of 8 built; recording is OFF until the owner switches it on)

Goal: staff do not open Dua or press a button; their phone notices arrival and departure and the server records them. **Rule, as everywhere: the phone reports, the server decides.** The owner has a switch (Attendance → Places and limits → "Record arrivals and leaving automatically", migration 1403, off by default). While it is off, phones only list what they detect ("Test mode"); nothing is recorded.

- **Detection (Phase 3).** After sign-in, Dua asks the server for the active places (`mgmt_attendance_my_site`: places, stay time, accuracy limit, the switch) and hands them to the phone (`DuaDevice.startAutoAttendance`). The phone registers one Google Play services geofence per place: **DWELL** (stayed inside for the stay time, default 120 s, owner-set 30–600 s) and **EXIT**. Google keeps watching while Dua is closed and the screen is locked. The Attendance page asks the server again when it opens, on "Check again" and after the owner saves, so a place added later reaches the phone without restarting Dua. A staff phone only learns of a changed place when that person opens Dua.
- **From detection to attendance (Phase 4).** With the switch on, a detection becomes work for WorkManager (survives the app closing and a restart):
  - *Arrived* (DWELL): take a **fresh high-accuracy location** (the geofence's own location is often only about 100 m accurate; the exit in the first test was 13 m, the arrivals about 100 m). Inside the place and accurate enough → queue an **in**. Not good enough → look again after 1, 2, 4, 8 minutes (5 tries); on the last try the event is sent anyway so the server records the refusal and the owner can see it.
  - *Left* (EXIT): wait the stay time, then take a fresh location. Still outside → queue an **out**, stamped with the time the phone left. Back inside (a flicker at the edge, or they returned) → **cancelled, nothing is sent**. A new arrival also cancels a pending leaving.
  - Time on the record: the moment the phone confirmed it (arrival = after the stay time inside; leaving = when the phone left).
- **Why a device key.** While Dua is closed the web login does not exist. So, like the widget, the phone gets its own secret (`app_device_attendance_enroll`, stored only as a SHA-256 hash; the phone keeps it in encrypted storage, pinned to our own `attendance-event` function). It can do one thing: report an arrival or a leaving. It is issued only when the switch is on, replaced when asked again, cleared when the phone changes hands, and **checked against the person's current `attendance.check_in` on every event** (lose the right → the next event is refused 401 and the phone stops).
- **What the server does with an event** (`app_attendance_event`, service role only, behind the Edge Function `attendance-event`): measures the distance itself; an **in** must be inside the place, an **out** must be outside (the opposite of the manual check-out); refuses a mock location, weak GPS, no place, wrong side (these appear to the owner as refused attempts, marked "Automatic"; a mock location also alerts the owner); **ignores** harmless repeats (an in while in, an out while not in, anything older than the last recorded event, anything over a day old or in the future) and keeps them in the history; never records the same **event id** twice (a phone that did not get the answer sends it again and gets the same answer). People are handled one at a time (advisory lock). A recorded event is an ordinary `mgmt_attendance` row with source `auto`, so every page and the night-shift handling work unchanged. Every event, whatever the outcome, is kept in `mgmt_attendance_auto_events` (append-only).
- **Offline.** Events wait in an encrypted queue (50 at most) and are sent when there is a network (WorkManager with a network constraint and growing wait; the 15-minute check also sends). The page shows how many are waiting.
- **Keeping it alive.** Android forgets geofences when the phone restarts, when Dua is updated, and when location is switched off. `BootReceiver` registers them again; `AttendanceWatchdogWorker` runs every 15 minutes (notices a lost permission, location off, or "Restricted" background use, tells the person once, registers again when fixed and once a day). Registering again while the person is inside produces one more "arrived"; the server ignores it as "already in" (but if the person checked out by hand and is still inside the place when a re-registration happens, it would record an arrival).
- **What the person must allow.** Precise location, location switched on, and location **"Allow all the time"**; Dua must not be "Restricted" in the battery settings ("Unrestricted" recommended). The page shows each item with a button that repairs it.
- **No foreground service, no always-on notification.** The price: Google may delay a transition by a minute or two, and some phone makers (Xiaomi, Oppo, Vivo, Huawei, Samsung "sleeping apps") kill background apps unless the person allows autostart or removes Dua from battery saving. The journal and the 15-minute check show whether it works on a given phone.
- **Sign-out and lost permission** wipe the places, the key, the queue and the journal and cancel pending work (`stopAutoAttendance`).
- **Radius.** Google recommends 100 m or more for reliable geofences; the database allows 20–2000 m.
- **Not built yet:** Phase 5 remainder (a staff phone fetching a changed place while Dua is closed; richer audit screens), Phase 6 owner alerts and health indicators (check-in/out notices, missed transitions, disabled permission, inactive device), Phase 7 real-phone test matrix, Phase 8 release.

## 5. Notifications (ntfy retired, Firebase instead)

Firebase Cloud Messaging is free with no message limit and no extra app on the phone. The flow is unchanged for modules: they call `notify_owner(...)`; rows land in `notifications`; a sender delivers them. Only the sender changed.

- **Who receives what** is the table `app_push_rules` (default: every alert goes to the owner / anyone holding `notifications.view`). Add a rule from SQL or `app_push_rule_set` (needs `settings.manage`), e.g. send closing alerts to people holding `closing.review`. No APK change.
- **Which phones**: `app_devices` (one row per install, created when the person signs in inside the app and allows notifications; removed at sign-out). A push address Firebase reports as dead is switched off automatically.
- **Alerts raised while no phone is registered** are recorded as *failed* with the reason "no device is registered", visible in the Cover's "Needs attention" and the Tools tab. They are never silent.
- **Privacy change to be aware of:** ntfy went through a public server; Firebase goes through Google. The message text is the same as before (closing and audit alerts carry the figures the owner approved in D-62 to D-64). If you would rather not send figures to Google, switch those alerts to the generic wording in `supabase/functions/_shared/ntfy.ts`.
- While the app is **open in the foreground** Android does not draw a tray notification for these messages (the Cover already shows the alert). In the background or closed, it does.

## 6. Today's Sale widget

Shows today's Candela total (Pakistan business day), "Updated 14:07", and for the owner the cash / card / credit split. Tap the figure to refresh, tap the title to open Dua. Android limits background refresh to every 15 minutes; Candela itself syncs hourly, so the widget is as live as the data is.

- **Who sees it**: the owner (`candela.view`) and anyone holding `candela.today_total` (the same key as the status-bar number). Staff get one number only, never the split.
- **Not "transaction count":** Candela's daily summary has no overall bill count (only credit receipts), so the widget does not show one. Adding it needs a feed change first.
- **How it signs in without the web login:** when the person opens the app, the web app asks the server for a random per-device secret (shown once, stored on the server only as a SHA-256 hash, kept on the phone in Android Keystore-encrypted storage). The widget sends that secret to `widget-today`; the database re-checks the person's **current** permissions on every call. Revoke the permission, disable the person, sign out, or sign in as someone else on the phone, and the widget stops at once. (It does not reuse the web token because Supabase rotates refresh tokens, so a widget renewing it would sign the person out of the app.)
- **Exception to MODULES.md rule 9** ("never cache sales totals on a staff phone"): the widget keeps the last figure in encrypted storage so it is not blank offline. It is wiped at sign-out and whenever the server refuses the secret. This is the one deliberate exception, and it exists because showing the figure on the home screen is the feature.

## 7. Gmail

Google blocks its sign-in inside an app's embedded browser, so **Send via Gmail is hidden in the APK** (`gmailAvailable()` in `js/core/gmail.js`; recognised by the native flag or the `DuaAndroid/` user-agent marker). It is unchanged on the website. "Copy", "Print" and the plain Email button still work.

## 8. Setup checklist (one time, in this order)

1. **Firebase** (free): console.firebase.google.com → create a project → add an Android app with package name `com.duapharma.dua` → download `google-services.json`.
2. **Service account**: Firebase → Project settings → Service accounts → *Generate new private key* (a JSON file).
3. **Supabase secrets** (Dashboard → Edge Functions → Secrets): `FCM_SERVICE_ACCOUNT` = the whole JSON from step 2. `NOTIFY_DRAIN_SECRET` and `OPS_REPORT_SECRET` already exist.
4. **Apply migrations** `0110` and `1401` to the live project (the owner applies migrations; do not re-run earlier ones).
5. **Deploy the Edge Functions** `notify-push` and `widget-today` (both with JWT verification off; `supabase/config.toml` records that).
6. **Signing key** (once, keep the file and passwords safe; losing them means users must uninstall to update): `keytool -genkeypair -v -keystore dua.keystore -alias dua -keyalg RSA -keysize 2048 -validity 10000`. Back it up somewhere other than GitHub.
7. **GitHub secrets**: `FIREBASE_GOOGLE_SERVICES_JSON_B64` (`base64 -w0 google-services.json`), `ANDROID_KEYSTORE_B64` (`base64 -w0 dua.keystore`), `ANDROID_KEYSTORE_PASSWORD`, `ANDROID_KEY_ALIAS`, `ANDROID_KEY_PASSWORD`.
8. **Build**: Actions → *Android APK* → Run workflow (or push a tag `android-v1.0.0` to also create a Release). Download `dua-<version>.apk` and its `.sha256`.
9. **Install** on one phone (allow "install unknown apps" for the browser/file app). Open it, sign in, allow notifications and location.
10. **Check on that phone** (§10), then roll out.

### Cutting over from ntfy (only after step 9 shows one registered device)

1. Point the cron job at the new sender (run in the SQL editor; no secret appears in it):
   ```sql
   select cron.alter_job(
     (select jobid from cron.job where jobname = 'notify-drain'),
     command := $job$
       select net.http_post(
         url := (select decrypted_secret from vault.decrypted_secrets where name = 'ops_function_base_url') || '/notify-push',
         headers := jsonb_build_object('Content-Type', 'application/json', 'x-ops-secret', (select decrypted_secret from vault.decrypted_secrets where name = 'notify_drain_secret')),
         body := '{"action":"drain"}'::jsonb, timeout_milliseconds := 10000)
       where exists (select 1 from public.notifications where status in ('pending', 'failed') and attempts < 5 and next_attempt_at <= now())
         and exists (select 1 from vault.decrypted_secrets where name = 'notify_drain_secret')
         and exists (select 1 from vault.decrypted_secrets where name = 'ops_function_base_url') $job$);
   ```
2. In `.github/workflows/backup.yml` change both `/notify-ntfy` calls to `/notify-push` (and `docs/RUNBOOK.md` §6 step 5).
3. Watch the Tools tab for a day. Once alerts arrive on the phone, remove `notify-ntfy` and the `NTFY_*` secrets in a separate change. **To roll back**, point the cron job back at `/notify-ntfy`; nothing else changed.

## 9. Security notes

- The APK opens only `https://dua.duapharma.com` (`allowNavigation`); cleartext, backup and web debugging are off. Only that site can call the native plugin.
- The widget secret and the Firebase service account never enter Git. `check-shell.mjs` fails the build if a `google-services.json` or keystore is in the tree, and the repo secret scanner still runs.
- A `google-services.json` holds Firebase's public client configuration, not a secret, but is kept out of the public repo anyway and written at build time.
- A site compromise would give an attacker the native plugin too (location, the widget secret). That is the cost of loading the live site, and the reason the web app's CSP and "no `innerHTML`" rules matter as much as they do.

## 10. Phone test script (do this before rollout)

1. Sign in as the owner. Allow notifications and location. Add the pharmacy place with a 100 m distance.
2. Sign in as a staff member who has `attendance.check_in`; check in while at the pharmacy → *Checked in*. Check out → *Checked out*.
3. Check in from outside the radius → refused with the distance; the owner receives "attendance attempt refused".
4. Turn on a fake-location app → refused as mock location.
5. Add the widget; tap the figure; compare it with the web Cover's Candela number. Staff widget shows one number; the owner's shows the split.
6. Remove the staff member's `candela.today_total` → within 15 minutes (or on tap) the widget stops showing a figure.
7. Raise a test alert (finish a test closing, or `select public.notify_owner('closing.submitted', '{}'::jsonb)`) → the phone shows it within about a minute, with the app closed.
8. Sign out → the widget goes blank and the phone receives no more of that person's alerts.
9. Open Reports → no *Send via Gmail* button inside the app; present on the website.
10. **Automatic attendance, detection (switch off).** Add the pharmacy place. On a staff phone with `attendance.check_in`, open Manager → Attendance in the app: the *Automatic attendance* card should say *Watching the pharmacy* once precise location and "all the time" are allowed (follow the buttons). Walk beyond the distance and stay out the stay time plus a few minutes with the screen locked and Dua closed: *Left* appears; walk back and stay: *Arrived*. Restart the phone and repeat. Switch location off: within about 15 minutes a notification says automatic attendance is off. (Nothing is recorded while the switch is off.)
11. **Automatic attendance, recording (switch on).** The owner ticks "Record arrivals and leaving automatically" and saves; open Dua once on the staff phone and press *Check again* (the phone gets its key). Then, with Dua closed and the screen locked: walk out, stay out the stay time plus a few minutes → the journal shows *Check-out recorded* and the owner's records show an Out with the source Automatic; walk back in and stay → *Check-in recorded*. Also try: step out for under the stay time and return → *Leaving cancelled*, no out recorded; switch on aeroplane mode, leave, wait, switch it off → the page shows an event waiting, then recorded; check in by hand while at the pharmacy, then walk in/out → no duplicate.
