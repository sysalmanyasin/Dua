D-41 Workspace access is per document. A person who holds `workspace.use` still sees only documents they own or that were shared with them (editor or viewer). D-42 Workspace note saving never overwrites. A save names the version the editor started from; if someone else saved since, nothing is applied and the editor's text is stored as an open conflict. Autosave updates a person's own newest version in place for five minutes, then seals it; sealed versions never change and nothing is deleted. Restore writes a new version. The note format (nodes, marks, link protocols, block ids, limits) is validated by the browser and by the database against one shared case file (`tests/fixtures/workspace-note-cases.json`, which also generates a SQL test).
D-43 Third-party code that is published as many ES-module packages is bundled once, outside the app, into a single file under `vendor/<module>/`: exact versions published at least 14 days earlier, a reproducible esbuild recipe (`build/BUILD.md`), licences in `LICENSES.txt`, and the SHA-256 in `tools/check-vendor.mjs`. `package.json` gains no dependency and the app gains no build step. First use: ProseMirror for Workspace Notes (19 Nov 2026). GPL-licensed libraries (HyperFormula) are not used; the repository has no LICENSE file.
D-44 Routes carry no ids (see `docs/MODULES.md` §3). Workspace keeps the open document's id in session storage (`dua.workspace.open`). Consequence: reload keeps the same note, but there are no shareable links. A router change that allows an id segment is a Foundation decision and has not been requested.
D-45 Workspace autosave resends a failed save with the same operation id and the same content before sending anything newer, so a lost reply cannot make a person conflict with their own earlier save. D-46 Workspace Sheets design (approved, not built; `docs/modules/workspace.design.md`): current cell state in a cell table keyed by stable row and column ids, an append-only operation log for ordering and retries, snapshots for restore; formulas are calculated only in the browser by a small custom engine and the server never stores results. D-47 A migration applied by hand is verified by comparing a hash of every function body with the locally tested copy (comments inside function bodies count). Workspace `1100` and `1101` were checked this way.
D-48 Staff PINs are **4 digits**, set by the owner and permanent (no first-login change). Supabase Auth refuses passwords shorter than 6, so the password Auth stores is `HMAC-SHA256(PIN_PEPPER, "pin:" + username + ":" + PIN)`; `PIN_PEPPER` is a server-only secret (32+ characters) that must never change once staff exist. Weak PINs are refused: 0000-9999 repeats, runs (1234, 7890, 4321), pairs (1212, 1122), years 1940-2030, and a few keypad favourites. Five wrong PINs lock the username for **1 hour** (30 per address per hour); the owner can unlock early. Trade-offs the owner accepted: the owner knows every PIN, so the activity log proves which login acted, not which person; anyone who knows a username can lock that person out for an hour. Older 6-digit PINs keep working (stored as typed) until the owner sets a 4-digit PIN for that person.
D-49 **No self sign-up.** The owner creates a login for a person already in the Staff Registry (Manager) with a username, role (Junior or Senior) and PIN; the login is linked to that registry row, so no duplicate person is created. `request-access`, `claim-account`, access requests and setup codes are removed; their tables stay as history. One login per person (unique index on `profiles.staff_id`).
